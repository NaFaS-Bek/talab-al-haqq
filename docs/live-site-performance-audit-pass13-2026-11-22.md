## Исправление без вмешательства в религиозные материалы
В `style.css` у двух локальных `@font-face` добавлено `font-display:swap`. Это даёт браузеру возможность показывать системный шрифт, пока скачивается локальный шрифт, и избегать длительного периода невидимого текста. Это **не уменьшает размер TTF** и не доказывает улучшение LCP до измерения опубликованной версии. Арабские религиозные тексты, дуа, транскрипции и правила чтения не менялись.

## Наблюдение за скоростью (новый измеритель)
`tests/site-performance-baseline.cjs` запускается в GitHub Actions вместе с Chromium и локальным HTTP-сервером. Он сохраняет `performance-local-baseline.json` в артефакты: время появления заголовка, TTFB документа, DCL, наблюдаемое LCP, ресурсы и объёмы исходных файлов для размеров экрана 390 и 1280 px.

**Только локальная воспроизводимая базовая линия:** скорости GitHub Actions зависят от нагрузки раннера; это не Core Web Vitals в реальном интернете и не результат Lighthouse для покупателей/читателей. Текущие большие файлы дополнительно отмечаются предупреждениями. Введён ограничитель роста `content.json` выше 4 МиБ; это бюджет технической безопасности, а не идеальный размер каталога.

## Отдельная проверка реального публичного домена
Создан ручной workflow `.github/workflows/live-site-audit.yml`, который запускается только с **подтверждённым владельцем HTTPS-адресом**, например в GitHub Actions → **Check published site (manual)** → **Run workflow** → `site_url`. Он использует `main`, проверяет HTTP 200 для ключевых учебных страниц, манифеста и файлов, сравнивает SHA-256 `app.js`, `style.css`, `data/content.json` с текущей веткой, снимает примерные времена запросов и отмечает базовые HTTP-заголовки безопасности и неподготовленный `sw.js`.

`tests/live-site-audit.cjs` не собирает личные данные, не следует на другие домены, не делает массовый обход внешних исламских источников и отклоняет непубличные/локальные адреса. Отчёт сохраняется как `live-site-report.json`. **Без проверенного адреса workflow не запускался**, выводить «публичный сайт работает» нельзя. Даже при успешном запуске он не проверяет все динамические состояния, офлайн-установку и реальное поведение людей.

## Остаётся открытым (в порядке важности)
1. **P1 — подтверждение реального адреса:** получить публичный HTTPS URL из Cloudflare Workers → Settings → Domains & Routes или от владельца; затем запустить `Check published site (manual)` и зафиксировать commit SHA/HTTP-результаты. Не публиковать персональные ключи или токены Cloudflare.
2. **P1 — готовая офлайн-сборка:** в исходном `sw.js` до сих пор `RELEASE=null`. Не обещать автономность, пока отдельный упаковщик не создал проверенные хеши всех страниц, шрифтов и JSON и пока установка/обновление не прошли браузерные тесты. Это следующий технический этап.
3. **P2 — большой initial payload:** рассмотреть разбиение каталога на разделы либо начальный тонкий индекс при сохранении идентификаторов и неизменности религиозных строк. Это требует отдельно проверить поиск, избранное, счётчики, историю чтения и офлайн.
4. **P2 — крупный шрифт:** предложить оптимизацию формата/подмножества только после проверки покрытия арабского, русского и специальных символов, совместимости устройств, источника лицензии и точности религиозной орфографии. В данном PR шрифтовые бинарники не менялись.
5. **P2 — живые Web Vitals:** Lighthouse и браузерные измерения на подтверждённом HTTPS URL, мобильный бюджетный аппарат, медленная сеть, кеш первого и повторного открытия.
6. **P2 — серверная безопасность:** реальные CSP, HSTS, MIME, заголовки, редиректы и политику кеширования можно достоверно проверить только на известном сайте.
7. **Содержание:** ни этот этап, ни успешные техтесты не являются независимым богословским удостоверением. В будущем отдельный аудиорежим потребует проверенного произношения Корана/дуа.
